# Attachment implementation

Messages carry a nullable `{schemaVersion: 1, items}` JSONB envelope. Local entries use `attachmentId` for the message and `localResourceId` for the device map; uploaded entries carry a real `fileId`. Paths and Base64 are absent from the envelope. Shared normalization merges legacy file/image lists without duplicate uploaded IDs. Create, paired create, batch import, update, addFiles, and file deletion keep uploaded JSON and `messages_files` in one transaction; uploaded ownership is checked before writes.

Desktop paperclip, paste and main conversation drag pass the topic to the same intake action. The current topic/draft execution intent chooses local intake. Preload captures the native File path before conversion; main only accepts an original reference when supplied File bytes match its contents. Pathless files go into managed draft storage. The device map validates realpath, device, size and content hash. Tool preparation copies to the topic scratch `.attachments/<localResourceId>/` directory and registers a topic binding. `validatePreparedLocalAttachment` supports main-process exact-file read grants. Original directories receive no grant from this flow.

At request assembly local documents produce an attachmentId/name/type/size manifest, without paths, native preparation or automatic full parsing. Office and readFile calls accept attachmentId; the desktop boundary resolves its existing device record and topic binding before preparing the exact managed file. The index stores a small attachmentId-to-localResourceId lookup, with a validated legacy-record fallback. For code fallback, runCommand accepts attachmentId and supplies the verified managed copy through ATTACHMENT_FILE. Attachment paths and their managed parent directories are redacted from tool results, including subsequent shell output; ordinary workspace paths retain their existing contract. Attachment content hashes stay internal; Office versions come from Office results, so a first Office call omits its optional version. Images are read as image data URLs at request time. Only latest-user selected images remain enabled by default; history images become explicit ID placeholders. A missing or mismatched frozen model snapshot rejects selected images. Historical Add to input uses the same visual capability gate as paperclip intake; preview stays independent. A non-vision model rejects selected images. Limits are 10 images, 10 MiB each, 8192 pixels per dimension, and 40 megapixels at intake. Native image encoding is cached by resource/version after verifying the source. OpenAI-compatible and Anthropic-compatible SDK fetch boundaries enforce a 20 MiB serialized request ceiling, including retries; this is independent of preprocessing and does not claim to reduce network payload through caching. Video fallback stays enabled independently.

Cloud bootstrap now uses ID directories and version-specific per-file markers. Downloaded bytes are size-checked and renamed before registration. New attachments are reconsidered on later calls; failed preparation is visible and retried.

Verification: shared envelope tests; real temporary-file/Blob identity, device and version tests; historical/current image context tests; image-hook video regression; true serialized fetch byte guard; DB create/update/file deletion suites; cloud bootstrap/retry tests. Full GUI, provider/proxy and packaged-app acceptance belongs to the separate acceptance report. The model request ceiling currently covers OpenAI and Anthropic compatible factories; other provider families require explicit adapters before claiming equivalent support.

## Attachment lifecycle follow-up

Historical local attachments now expose Preview and Add to input in the existing message content. Add to input reuses the normal upload/file-list state and explicitly reselects historical images for the next request. Initial rendering performs index/stat checks only; image bytes or document preview paths are resolved after a user click. Other devices show an unavailable label with a reselect instruction.

New device index records track draft leases and message bindings. Input cancel, individual removal and queued-message cancel release draft leases. Successful sends transfer them to message bindings; message deletion releases only the deleted message's binding after the server confirms success. Managed draft/cache directories and index entries are removed only after the last tracked reference disappears. Original paths are never deletion targets. Legacy index records without lifecycle metadata are retained conservatively because older references cannot be reconstructed safely.

Focused single-worker verification: native attachment identity/cleanup/shared-reference concurrency 5/5; upload and historical re-add plus lazy-preview UI 12/12; message/queue regression 100/100, including confirmed-versus-failed message deletion. Input cancellation during pending re-add releases its newly acquired lease and does not resurrect the input item. These are unit results, not Electron acceptance. Real preview, historical-image resend, cross-device labels, input/queue cancellation and shared-message deletion still require the root-managed remote image plus rebuilt Electron acceptance run.
