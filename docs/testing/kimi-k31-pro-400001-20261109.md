# Kimi K3.1 Pro 400001 排查与修复

2026-11-09，在最新 main `be3e7172e244dc6d640150ad6c73f74ca66bef2a` 的独立 worktree / 分支 `codex/fix-kimi-k31-pro-parameters` 完成。没有部署、构建 Docker 镜像或修改线上配置。

根因已经通过单变量实验确认：客户端使用通用助理默认 `top_p=1`，`kimi-k3.1-pro` 未登记到 NewAPI 的 Kimi 专用运行时，因而这个字段被原样发送给腾讯 TokenHub。该上游要求固定 `top_p=0.95`，错误值触发 HTTP 400 / `400001`；Masterino 将 provider 业务错误包装成前端 HTTP 471。模型可用，账号有权限，错误与 1M 容量维护、静默刷新无关。

代码链路：`packages/const/src/settings/agent.ts` 的默认参数包含 `temperature=1`、`top_p=1` 和两个为 0 的 penalty；测试助理实际保存值相同。浏览器通过真实点击选择 Kimi 并发送 `Reply OK. Do not call any tools.`，从 Chrome DevTools 导出实际 `/webapi/chat/newapi` 请求。参数正是上述默认值，stream=true；没有 tools、max_tokens 或容量字段。测试服务日志包含该操作的 `ProviderBizError` / `400001`。原请求保留全部消息重放，稳定产生同一错误，脚本退出码为 1。

NewAPI 原路由只登记 `kimi-k2.7-code`、`kimi-k3`，漏掉精确 ID `kimi-k3.1-pro`。用真实 `LobeNewAPIAI.chat()` 配置合成 fetch 捕获 SDK 边界，观察到 K3.1 Pro 出站仍有 `top_p=1`，而 K3 / K2.7 Code 已省略采样参数。问题位于运行时选路，不是后台显示名称或 Aihub 模型权限。

腾讯官方 [Kimi 调用指南](https://cloud.tencent.cn/document/product/1823/132232) 的 K3 / K3.1 Pro 参数表与实验一致：采样值固定，建议省略；K3 系列用 reasoning_effort 和 max_completion_tokens，不能直接套用 K2.7 Code 的 thinking 配置。

修复将精确 ID K3.1 Pro 接入既有 Kimi 运行时，省略固定采样字段（包括 n），按 K3 协议转换 max_tokens、保留 reasoning_effort，并不向 K3 系列添加 K2.7 Code 的 thinking 开关。K2.7 Code 仍保留 thinking=enabled 与 max_tokens；模型 ID、路由目标、权限、模态、价格及原始消息保持原意。

新增 SDK 边界回归先失败：K3.1 Pro 漏选路，K3 原适配还保留了不合法的 n=2。修复后路由测试覆盖两个精确 K3 ID、K2.7 Code 的 reasoning/tool continuation、普通模型及相似但不匹配的自定义 ID。4 组定向运行时测试 99 通过、1 个既有跳过；完整 type-check、变更文件 lint 和格式检查通过。
